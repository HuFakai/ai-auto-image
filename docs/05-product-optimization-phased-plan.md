# 产品优化分阶段开发方案

> 版本：2026-09-01  
> 状态：阶段 A、B、C、D、E、F 已完成；阶段 G 待执行
> 适用范围：余额门禁、失败恢复、原生图片单一路径、账务可追溯、模型目录与按次计费  
> 当前生产基线：Docker + PostgreSQL + 进程内 Runner；本方案不要求提前引入 Redis 或独立 Worker。

## 1. 目标与范围

本轮把以下七项需求拆成可独立开发、验证和上线的阶段：

1. 点击“开始创作”时检查点数，低于 6 点时阻止创建并引导充值。
2. 为余额不足、渠道失败等失败作品提供从头重试、检查点恢复和单图重试。
3. 删除确定性文字排版/渲染，仅保留 AI 原生生图。
4. 点数明细与我的订单支持分页，点数明细可追溯到任务/作品。
5. 用户订单展示订单号，管理后台可按订单号查询。
6. 管理员调整点数同步形成用户和后台可见的“调整订单”，标题采用调整备注。
7. 建立渠道模型目录、模型发现、多选启用、能力标记、优先级、用户选模和按模型按次计费。

本方案定义开发顺序、技术边界和验收口径；阶段 A–E 已按本方案落地，后续阶段继续按“完成一阶段、最小验证、提交推送”的节奏实施。

## 2. 现状结论与关键决策

### 2.1 当前实现中的主要差距

- 创建接口当前只预检 1 点，真正工作流按图片数量预留点数，因此低余额用户仍会先产生失败作品。
- Job 有最大尝试次数并会进入终态；恢复失败任务不能“复活”原 Job，应创建新的恢复 Job。
- 工作流节点和页面已经具有一定幂等性，可作为检查点恢复的基础；单页重生成接口目前只允许成功作品调用。
- 确定性渲染不仅存在于创作选项，还涉及知识卡片/漫画/封面/平台适配、详情页免费重排、品牌预览、渲染引擎与字体资源，必须按依赖完整删除。
- 用户订单和点数流水均只取最近 20 条；点数流水只记录节点引用，不能稳定显示作品名称。
- 管理员调点只写钱包与流水，没有订单记录；后台订单搜索只覆盖标题。
- 一个渠道当前只保存一个文本或图片模型，无法支持模型发现、多选、模型级能力和模型级价格。
- 当前仅图片成功调用扣点，文本调用免费；如果改为“文本和图片均按次计费”，计费必须下沉到每次真实网络调用。

### 2.2 本轮必须统一的产品语义

| 主题 | 统一规则 |
| --- | --- |
| 6 点门槛 | 6 点是创建准入下限，不代表整个作品的最终价格；服务端为最终裁决，前端余额仅用于提前提示。 |
| 从头重试 | 基于原输入创建一个新 Run，保留原失败作品和审计记录，并记录来源关系。 |
| 检查点恢复 | 在同一个失败 Run 上创建新的 Job，跳过已成功且资产有效的节点/页面。 |
| 单图重试 | 只重生成指定失败或缺失页面，成功后重新判断作品是否可继续包装并完成。 |
| 确定性渲染 | 新任务和重试任务全部使用原生 AI 生图；历史成品继续可查看和下载，不批量删除历史资产。 |
| 管理员调点订单 | 作为 `admin_adjust` 类型的非支付订单展示，金额为 0，不进入收入、支付成功率和退款统计。 |
| 用户指定模型 | 指定后硬绑定该模型，不静默切换其他模型；“自动选择”模式才允许按优先级故障转移。 |
| 模型能力 | `/models` 返回值通常不包含可靠能力，图生图等能力由管理员确认，前后端都必须校验。 |
| 模型价格 | 使用非负整数点数，按成功的真实模型调用计费；失败调用释放预留，不向用户扣点。 |
| 价格变更 | 运行开始时冻结模型、能力和价格快照，后台改价只影响新任务。 |

## 3. 优先级、复杂度与依赖顺序

| 阶段 | 内容 | 优先级 | 复杂度 | 预计工作量（单人） | 主要依赖 |
| --- | --- | --- | --- | --- | --- |
| A | 余额准入与友好提示 | P0 | 低 | 0.5–1 天 | 无 |
| B | 删除确定性文字排版 | P0/P1 | 中高 | 2–4 天 | A 可并行，但应先于恢复体系完成 |
| C | 作品/检查点/单图重试 | P0/P1 | 高 | 3–5 天 | B、现有节点幂等能力 |
| D | 账务分页、作品追溯、调点订单 | P1 | 中 | 2–4 天 | PostgreSQL 迁移 |
| E | 模型目录、发现、能力与优先级 | P1 | 高 | 4–6 天 | D 的账务字段约定 |
| F | 用户选模与模型级按次计费 | P1/P2 | 很高 | 5–8 天 | E、调用级计费事件 |
| G | 联调、迁移与灰度发布 | P0 发布门禁 | 中高 | 2–4 天 | A–F |

总量约 18–32 个工程日。A 可以单独快速上线；B/C、D、E/F 应分别作为可回滚版本发布，不建议一次性合并到生产。

依赖主线如下：

```text
余额准入 → 原生生图单一路径 → 失败恢复
                    └──────────→ 账务追溯 → 模型目录 → 用户选模与按次计费
```

## 4. 阶段 A：余额准入与充值引导（P0）

### 4.1 开发内容

- 在“开始创作”按钮点击后，先读取最新余额；余额少于 6 点时直接打开余额不足提示。
- 提示中展示当前余额、最低需要 6 点和“前往充值”按钮，不创建 Project、Run 或 Job。
- 创建 API 增加服务端 `minimumCredits = 6` 校验，返回稳定错误码、当前余额和最低门槛。
- 前端缓存余额只负责改善交互；即使前端判断通过，服务端仍必须二次校验并处理并发消费。
- 错误信息改为中文产品文案，不再直接向用户显示 `InsufficientCreditsError` 堆栈或内部类名。

### 4.2 测试与验收

- 余额 0、2、5：点击后不创建任何作品，弹窗可跳转充值中心。
- 余额 6：允许进入创建流程；后续实际所需点数更高时仍由工作流增量预留保护余额。
- 两个标签页同时创作：服务端事务校验确保不会透支。
- 验收数据库中不存在因“准入余额不足”产生的空 Project、失败 Run 或 Job。

### 4.3 后续演进

阶段 F 上线动态模型价格后，6 点仍保留为最低门槛，同时在提交前显示估算费用；服务端按冻结价格和实际调用逐次预留，不能用前端估价代替事务扣费。

## 5. 阶段 B：删除确定性文字排版（P0/P1）

### 5.1 删除范围

- 删除创作条中的文字渲染模式开关及新建任务的 `textRenderingMode` 参数。
- 删除知识卡片、漫画、封面和单页重生成中的 deterministic/auto-fallback 分支，新任务统一走 native。
- 删除详情页“免费重排/重新排版”入口、确定性重排 API 和相关提示。
- 平台适配不再做免费确定性改版：改为付费的原生 AI 全作品重生成；若暂时无法一次完成，则先隐藏该入口。
- 品牌手册预览改用静态预览图或独立的后台预览组件，不能继续依赖生产确定性内容渲染器。
- 删除不再被使用的确定性渲染函数、模板、字体复制步骤和测试夹具；Sharp 等仍被资产校验或图像处理使用的依赖不得误删。
- 将 ADR-0003 标记为“已被原生生图单一路径取代”，同步更新 README、部署文档与当前路线图。

### 5.2 兼容与迁移策略

- 数据库和历史输入先保留旧枚举读取兼容，旧作品继续展示其已生成资产。
- 新建、从头重试、检查点恢复和单页重试均强制使用 native，不再调用确定性路径。
- 不对历史 JSON 做破坏性批量重写，不删除历史字体/图片资产；确认至少一个版本无读取依赖后再清理废弃字段。

### 5.3 验收门禁

- 全仓搜索不再存在可执行的 deterministic 生成入口。
- 所有内容类型、封面候选、单页重试、平台比例重生成均只走 AI 图片渠道。
- Docker 构建不再依赖已删除的字体目录，历史作品仍能打开、预览、下载。
- 更新后的单元、集成和构建测试全部通过。

## 6. 阶段 C：失败恢复与单图重试（P0/P1）

### 6.1 数据和状态设计

- 新增 Run 来源关系：`retryOfRunId` 或独立 `run_relations`，用于展示“由某次失败任务从头重试”。
- 检查点恢复不修改终态 Job，使用唯一幂等键创建新 Job，并记录恢复序号、触发用户和恢复模式。
- 为页面生成结果记录结构化失败原因：余额不足、429、Provider 5xx、超时、内容拒绝、下载/校验失败、未知错误。
- Run 的 `failed → running → succeeded/failed` 状态转换必须由服务端原子执行，并保留上一次失败摘要。

### 6.2 API 设计

- `POST /api/runs/{id}/retry`
  - `mode=checkpoint`：复用已成功节点与有效资产，在原 Run 上创建恢复 Job。
  - `mode=restart`：复制冻结输入创建新 Run，原 Run 保持失败状态，响应返回新 Run ID。
- 扩展 `POST /api/runs/{id}/pages/{index}/regenerate`：允许失败 Run 的失败/缺失页面调用，成功页面也可主动重生成。
- 所有重试接口校验作品归属、余额、模型可用性、重复点击幂等和当前是否已有运行中 Job。
- 单图成功后执行状态协调：若仍有失败页面则保持失败；若全部页面成功则自动排队继续包装/导出并最终完成。

### 6.3 详情页交互

- 作品级错误区域显示可理解的原因和处理建议；余额不足提供充值按钮，渠道错误提供稍后重试提示。
- 增加“重新生成”主按钮，弹出：
  - 从检查点继续：保留已成功文本、分镜和图片，速度更快、消耗更少。
  - 从头开始：创建新作品，不覆盖原失败记录。
- 每个失败图片卡片显示失败原因和“重新生成此图”；生成中禁用重复提交并显示状态。
- 恢复完成后刷新页面、发布文案、导出包与点数余额，不要求用户手动重新进入详情页。

### 6.4 计费和验收

- 检查点恢复只为新的实际模型调用扣点，已成功且复用的内容不得重复收费。
- 失败 Provider 调用释放预留；成功的单图重试按所选模型价格扣点。
- 覆盖断电重启、重复点击、并发恢复、成功回调重复到达和“扣点成功但页面写入重试”等场景。
- 至少用余额不足、模拟 429、模拟图片下载失败三个案例验证三种恢复方式。

### 6.5 阶段 C 实施结果（2026-09-01）

- ✅ `POST /api/runs/{id}/retry` 支持检查点恢复和从头创建新作品。
- ✅ 失败页面保存页码与错误摘要；详情页可单独重试失败页面，漫画页面也支持目标页恢复。
- ✅ 检查点恢复创建新 Job，不复用已失败 Job；成功节点和现有资产按幂等逻辑复用。
- ✅ 恢复后重新生成 manifest，并在全部页面补齐后恢复为成功/待审核状态。
- ✅ 已通过工作流、漫画恢复、存储仓库最小测试及 workflow/web 类型检查；完整门禁留到阶段 G。

## 7. 阶段 D：账务可追溯与分页（P1）

### 7.1 数据迁移

- 点数流水新增 `runId`、`displayTitle`（作品/调整标题快照）等字段；新消费写入 Run ID 和作品名。
- 旧流水通过节点 → Run → Project 尽力回填作品名；无法回填时显示原 `note/reason`，不伪造关联。
- 订单新增 `type/source` 字段，至少区分 `payment`、`subscription`、`admin_adjust`；必要时增加操作管理员 ID。
- 管理员调整点数时，在同一数据库事务内完成钱包变更、流水记录和 `admin_adjust` 订单创建，使用唯一业务键防重复。

### 7.2 查询接口与 UI

- 新增分页接口：
  - `GET /api/billing/ledger?page=1&pageSize=20`
  - `GET /api/pay/orders?page=1&pageSize=20`
  - 管理后台订单接口同步返回 `items/total/page/pageSize/totalPages`。
- 排序统一为 `createdAt DESC, id DESC`；页大小限制在 10–100，避免一次性加载过多。
- 充值中心“点数明细”和“我的订单”增加分页、加载态、空态和总条数。
- 点数明细展示作品/任务名称；消费标题建议为“《作品名》· 图片模型调用”或“《作品名》· 文本模型调用”。
- 用户订单展示可复制订单号；后台订单支持订单号精确/模糊搜索，并保留标题筛选。
- 管理员调整订单标题和点数流水标题均直接显示调整备注；备注为空时服务端拒绝提交。

### 7.3 统计隔离与验收

- `admin_adjust` 金额固定为 0，可包含正负点数，不出现支付、退款、关闭订单等操作。
- 每日收入、累计收入、支付成功率和支付渠道构成必须排除 `admin_adjust`。
- 用户、管理员看到的调整订单号、备注、点数和时间一致；钱包、流水、订单任一写入失败时整笔事务回滚。
- 10 万条流水的分页查询应使用用户/时间、订单号等索引，避免全表扫描。

### 7.4 阶段 D 实施结果（2026-09-01）

- ✅ 新增流水 `runId`、作品/调整标题快照，迁移会尽力回填历史生图流水的 Run 与作品名。
- ✅ 充值中心点数明细、我的订单和后台订单统一使用分页结果；用户订单展示订单号，后台搜索同时匹配标题与订单号。
- ✅ 管理员调点在单一数据库事务中完成钱包、流水和 `admin_adjust` 订单写入，正负调整均保留备注与操作管理员。
- ✅ `admin_adjust` 使用独立的“已调整”状态和后台渠道，不进入收入日统计、渠道收入或支付订单退款流程。
- ✅ 已通过 storage Repository/事务分页测试、billing 标题追溯测试及 storage/web 类型检查；完整门禁留到阶段 G。

## 8. 阶段 E：模型目录、模型发现与优先级（P1）

### 8.1 数据模型

新增 `channel_models`，渠道继续只负责密钥、Base URL、协议、重试和并发；模型表至少包含：

- 渠道 ID、Provider 模型 ID、展示名称、文本/图片类型。
- 启用状态、默认状态、是否允许用户选择、模型优先级。
- 单次消耗点数（非负整数）。
- 图生图、单图编辑、多图参考等能力标记和扩展能力 JSON。
- 发现时间、最近确认时间、是否已从最新发现结果中消失。

渠道新增显式 `priority`：数字越大越优先；同优先级按模型优先级、原显示顺序和稳定 ID 排序。迁移时把每个旧渠道当前配置的单模型写入模型表，并保留为默认模型。

### 8.2 管理后台功能

- 增加“获取模型”按钮，服务端使用加密保存的渠道凭据请求兼容 `/models` 接口。
- 返回列表经过去重、超时、响应大小和字段校验后展示；管理员可多选启用，不因本次列表缺失而直接删除历史模型。
- 每个模型可设置展示名、启用、默认、优先级、消耗点数和能力。
- 每个渠道增加“允许用户自定义模型”开关；初次上线默认关闭，阶段 F 才向创作端公开模型目录。
- 渠道/模型测试结果展示可诊断错误，但不得返回完整 API Key、请求签名或敏感响应。

### 8.3 能力与路由规则

- `/models` 提供的 ID 不能自动证明图生图能力；系统可以给出名称提示，但必须由管理员确认能力。
- 阶段 E 先让渠道优先级生效，并保存模型优先级；阶段 F 接入多模型路由后，自动模式再按渠道优先级、模型优先级故障转移。
- 用户指定模型时硬绑定，不在后台静默改成另一模型；不可用时返回明确错误并允许用户重新选择。
- 渠道并发仍是项目唯一并发限制：`0` 表示不限，正整数表示该渠道所有用户共享上限。

### 8.4 验收

- OpenAI-compatible、OpenAI、xAI 三类渠道至少各验证一次模型发现成功/失败路径。
- 列表重复获取不产生重复模型；停用、改价、改优先级有管理员审计记录。
- 关闭用户自定义开关时，创作端不泄露模型列表且继续使用自动默认路由。

### 8.5 阶段 E 实施结果（2026-09-01）

- ✅ 新增 `channel_models` 模型目录和 `0009_channel_model_catalog` 迁移；旧渠道的 `text_model/image_model` 会回填为已启用的默认模型，升级后现有路由行为不变。
- ✅ 后台渠道支持优先级、模型目录获取、模型多选启用、默认模型、模型优先级、单次消耗点数和图生图能力标记。
- ✅ 新增 `GET/POST/PUT /api/channels/{id}/models`：获取供应商 `/models` 会去重、限时、限制响应体大小；新增模型默认关闭，重复获取不覆盖管理员的价格、能力和选择状态。
- ✅ 渠道新增“允许用户在创作条自定义选择模型”开关，默认关闭；模型级价格和能力已保存，阶段 F 接入创作条和调用级计费。
- ✅ 模型渠道路由按渠道优先级降序装配；渠道并发仍是唯一运行时并发限制，默认 `0` 不限制。
- ✅ 已通过模型目录仓储回归测试、渠道配置 Schema 测试及 storage/web 类型检查；完整门禁留到阶段 G。

## 9. 阶段 F：用户选模与模型级按次计费（P1/P2）

### 9.1 创作端选模

- 提供只含公开字段的模型目录接口，不返回 Base URL、密钥或内部错误。
- 全局开关开启后，在创作条增加文本模型和图片模型选择器，保留“自动选择”。
- 每项显示模型名称、单次点数和关键能力；切换内容类型时重新过滤图片模型。
- 对要求图生图/角色一致性的内容类型，只展示支持对应能力的图片模型；提交 API 再次执行同样校验。
- 在 Run 输入快照中保存选择的模型 ID、解析后的渠道/Provider 模型 ID、能力和价格快照。

第一版能力矩阵至少覆盖科普漫画、四格漫画等依赖参考图/图生图的类型；后续新增内容类型必须同步声明能力要求。

### 9.2 调用级计费架构

新增模型调用计费记录（可命名为 `model_call_charges`），包括：

- 用户、Run、节点、Provider Attempt、渠道模型、模型名快照。
- 点数、状态 `reserved/captured/released/uncertain`。
- 唯一幂等键、创建/完成时间和失败分类。

每次真实文本或图片 HTTP 调用执行：

1. 按冻结价格原子预留点数。
2. 发起 Provider 调用并写调用尝试。
3. 获得可用成功响应后结算并生成点数流水。
4. 429、5xx、网络失败、内容拒绝等明确失败时释放预留。
5. 超时但无法确定 Provider 是否已处理时标记 `uncertain`，进入对账或安全重试流程，避免重复扣费。

结构化 JSON 修复、空响应后的再次请求、图片编辑回退等只要实际再次请求模型，都算新的“调用”；因此现有只记录外层路由尝试的方式必须下沉到网络调用层。

### 9.3 价格估算和重试规则

- 提交前展示估算费用：已知文本调用数 × 文本模型价格 + 最小页面数 × 图片模型价格 + 封面/漫画参考调用。
- 分镜完成前页数可能未知，UI 必须标注“预计”，不能承诺固定总价。
- 运行过程中仍逐次预留；中途余额不足时保留检查点，充值后从检查点恢复。
- Provider 自身失败重试不扣点，只有得到可用结果的实际调用结算；用户主动重新生成且成功则按新调用收费。
- 自动模式若发生模型故障转移，必须使用 Run 中冻结的候选与价格快照，并在详情页显示最终实际使用模型和费用。

### 9.4 验收

- 文本、图片、图生图、自动路由、用户指定模型分别完成成功/失败/重试/余额不足计费测试。
- 重复回调、进程重启和并发执行不能重复扣点；钱包余额应等于所有已结算流水之和。
- 后台改价后，运行中的任务价格不变，新任务采用新价格。
- 关闭用户选模开关后，已有 Run 仍按冻结快照完成，新建任务恢复自动路由。

### 9.5 阶段 F 实施结果（2026-09-01）

- ✅ 创作条接入文本/图片模型选择器；只有后台开启用户选模的渠道和已启用模型会公开，自动选择仍为默认路径。
- ✅ 科普漫画、四格漫画等需要图生图的内容类型，会过滤不支持单图编辑的图片模型；服务端创建和恢复流程会再次校验，不能靠客户端绕过。
- ✅ Run 保存用户选择的模型、渠道、Provider 模型 ID、能力和单次点数快照；后台后续改价不会影响该选择的运行。
- ✅ 文本模型每次成功调用按实际路由价格结算，失败/回退尝试释放预留；图片、封面、图生图和返修统一按实际成功路由价格结算。
- ✅ 发布文案生成也复用按次预留/结算/释放，并缓存已生成的 LLM 文案，避免详情页反复进入时重复调用和扣点。
- ✅ 已通过 shared-schemas、storage、workflow-engine、web 定向类型检查；workflow-engine 40 项、web 41 项相关回归测试通过。

说明：本阶段先复用现有 Run 预留、节点幂等和点数流水完成按次计费；独立 `model_call_charges` 明细、超时不确定状态和自动路由全候选价格快照属于阶段 G 的账务加固项。

## 10. 阶段 G：迁移、灰度与发布门禁

### 10.1 上线顺序

1. 先执行只增不删的数据库迁移和索引，完成旧数据回填报告。
2. 上线 A；观察失败作品数量和余额拦截日志。
3. 上线 B/C；用内部账号验证三类失败恢复，再向小范围用户开放。
4. 上线 D；核对钱包、流水、订单和收入报表。
5. 上线 E，但保持用户选模开关关闭，先维护模型目录和价格。
6. 上线 F，仅对白名单用户开启；完成真实小额点数测试后全量开放。
7. 至少稳定一个发布周期后，再删除旧确定性字段和兼容读取代码。

### 10.2 统一发布门禁

- `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 全绿。
- PostgreSQL 迁移可重复执行，备份可恢复；PGlite 测试路径同步更新。
- 钱包、流水、订单、模型调用计费记录完成一致性对账。
- Docker 镜像在 4 核 24G 服务器完成构建、健康检查、重启恢复和并发测试。
- API 错误不暴露密钥、完整 Provider 响应、内部堆栈或数据库信息。
- 旧作品可读、新作品可重试、失败不重复收费、管理员调点不污染收入。

### 10.3 回滚原则

- 每阶段使用功能开关隔离新入口；数据库优先做可兼容的新增字段/表，不在同一版本立即删除旧列。
- 失败恢复和用户选模可单独关闭，已运行任务仍按冻结快照继续。
- 模型计费启用前先跑影子计费：只记录应扣点，不改变钱包；与旧账本对比通过后再切换真实结算。
- 不通过直接改库修复钱包差异，统一通过可审计的管理员调整事务处理。

## 11. 完成定义

本计划全部完成时，应同时满足：

- 余额不足不会产生空失败作品，用户可直接进入充值。
- 失败作品可以从头、从检查点或按单图恢复，且不重复扣费。
- 项目运行时不存在确定性文字排版入口，新旧作品兼容可读。
- 任一点数变化可从钱包追溯到流水、作品/任务、订单或管理员备注。
- 管理员可发现和维护多个模型、能力、优先级和价格。
- 用户选模受后台开关控制，图生图能力过滤可靠，文本和图片按成功调用计费。
- 生产收入统计只包含真实支付，管理员调点有独立清晰的审计语义。
